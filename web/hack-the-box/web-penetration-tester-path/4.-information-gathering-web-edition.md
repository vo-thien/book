## whois

whois là giao thức để truy cập tới DB lưu trữ thông tin về tài nguyên internet đã được đăng ký



Bản ghi whois chứa các thông tin

* domain name: Chính tên miền đó
* registrar: Công ty nơi tên miền được đăng ký
* registrant contact: Cá nhận hoặc tổ chức đăng kí domain
* administrative contact: Người chịu trách nhiệm quản lý domain
* technical contact: Người xử lý các vấn đề kỹ thuật liên quan đến domain
* creation and expiration dates: Ngày đăng ký và ngày hết hạn của domain
* name servers: Máy chủ chuyển đổi domain thành ip



{% code overflow="wrap" lineNumbers="true" expandable="true" %}
```bash
whois inlanefreight.com
```

## dns

Hệ thống tên miền có vai trò chuyển đổi domain thành địa chỉ ip

### Cách DNS hoạt động (Recursive Lookup)

1. Máy tính kiểm tra cache DNS cục bộ (trong RAM, file hosts) ⇒ Nếu có thì dùng ngay
2. **DNS Resolver (Recursive Resolver)**: Thường mà máy chủ DNS của ISP (hoặc 8.8.8.8, 1.1.1.1). Resolver cũng kiểm tra cache của nó
3. **Root Name Server**: Nếu chưa có, resolver hỏi 1 trong 13 root server. Root server không biết chính xác IP nhưng biết TLD[^1] server nào chịu trách nhiệm
4. **TLD Name Server**: Sẽ trả về địa chỉ của Authoritative Name Server cho domain cụ thể
5. **Authoritative Name Server**: Server này nắm giữ địa chỉ ip chính xác và gửi về cho Resolver
6. Resolver nhận được ip và đưa cho máy tính. IP sẽ được cache 1 thời gian phòng trường hợp truy cập lại trang web sớm
7. Máy tính dùng ip để kết nối trực tiếp với web server

### Hosts File

Dùng để ánh xạ domain sang địa chỉ IP, bỏ qua quy trình DNS. File này sẽ được ưu tiên sử dụng.

* Vị trí
  * **Windows**: C:\Windows\System32\drivers\etc\hosts
  * **Linux / macOS**: /etc/hosts



### Zone và Zone File

**Zone**: Phần không gian tên miền do một tổ chức quản lý (VD: Toàn bộ example.com và các subdomain)

**Zone File**: File text trên Authoritative DNS Server chứa tất cả thông tin

{% code overflow="wrap" lineNumbers="true" expandable="true" %}
```
Ví dụ về Zone File

$TTL 3600
@       IN SOA   ns1.example.com. admin.example.com. (
                2024060401 ; Serial
                3600       ; Refresh
                900        ; Retry
                604800     ; Expire
                86400 )    ; Minimum TTL

@       IN NS    ns1.example.com.
@       IN NS    ns2.example.com.
@       IN MX 10 mail.example.com.
www     IN A     192.0.2.1
mail    IN A     198.51.100.1
ftp     IN CNAME www.example.com.
```
{% endcode %}

* Định nghĩa Authoritative Name Server (Bản ghi NS)
* Định nghĩa mail server (Bản ghi MX)
* Định nghĩa địa chỉ IP (Bản ghi A)

### Một số khái niệm DNS phổ biến

DNS Resolver: Máy chủ chuyển đổi domain thành ip (DNS Server của ISP hoặc resolver công cộng như 8.8.8.8)

Root Name Server: Máy chủ cấp cao nhất trong hệ thống phân cấp DNS (13 server trên toàn thế giới, đặt tên từ A-M: a.root-servers.net, ...)

TLD Name Server: Máy chủ chịu trách nhiệm cho các domain cấp cao nhất (.com, .org, ...)

Authoritative Name Server: Lưu giữ địa chỉ ip thực tế của một domain (Thường được quản lí bởi nhà cung cấp hosting or nhà đăng ký domain)

DNS Record Types: Các loại thông tin khác nhau được lưu trữ trong DNS (A, AAAA, CNAME, MX, NS, TXT, ...)

### Các loại DNS Record

A: Map hostname -> ipv4

AAAA: Map hostname -> Ipv6

CNAME: Alias trỏ đến tên máy chủ khác

* Ví dụ `blog.example.com. IN CNAME webserver.example.net` ⇒ Khi ai đó hỏi IP của blog.example.com, DNS sẽ trả về đây là CNAME trỏ tới `webserver.example.net` ⇒ Resolver tiếp tục hỏi IP của `webserver.example.net`

MX: Mail server cho domain (Có priority)

NS: Chỉ định Authoritative Name Server (Bất kỳ ai muốn biết IP thật cần phải hỏi NS)

TXT: Dữ liệu text tùy ý (Thường dùng để xác minh tên miền hoặc chính sách bảo mật)

SOA: Chỉ định thông tin quản trị về 1 zone DNS

SRV: Định nghĩa tên máy chủ và số cổng cho các dịch vụ cụ thể

PTR: Sử dụng cho reverse DNS lookup (Ánh xạ địa chỉ IP thành domain)

## Virtual Hosts

Các web server được thiết kế để lưu trữ nhiều website trên một máy chủ duy nhất thông qua virtual hosting

* Tận dụng HTTP Host Header

{% code overflow="wrap" lineNumbers="true" expandable="true" %}
```
# Ví dụ cấu hình name-based virtual host trong Apache
<VirtualHost *:80>
    ServerName www.example1.com
    DocumentRoot /var/www/example1
</VirtualHost>

<VirtualHost *:80>
    ServerName www.example2.org
    DocumentRoot /var/www/example2
</VirtualHost>

<VirtualHost *:80>
    ServerName www.another-example.net
    DocumentRoot /var/www/another-example
</VirtualHost>
```
{% endcode %}

<figure><img src="../../../.gitbook/assets/image (118).png" alt=""><figcaption></figcaption></figure>



Có 3 loại virtual hosting chính

* **Name-Based Virtual Hosting**: Chỉ dựa vào Host Header để phân biệt các trang web
* **IP-Based Virtual Hosting**: Gán địa chỉ IP duy nhất cho mỗi website được lưu trữ trên máy chủ
* **Port-Based Virtual Hosting**: Các website khác nhau được liên kết với các cổng khác nhau trên cùng địa chỉ IP

## Certificate Transparency Logs

Giao thức SSL/TLS mã hóa giao tiếp giữa trình duyệt và website

Certificate Transparency Logs là sổ ghi công khai, chỉ cho phép ghi dữ liệu ⇒ Ghi lại việc cấp phát chứng chỉ SSL/TLS

Khi Certificate Authority (CA) cấp chứng chỉ mới ⇒ Chứng chỉ đó phải được gửi tới nhiều CT log



### Cách hoạt động

1. Chủ sở hữu website yêu cầu chứng chỉ SSL/TLS từ CA ⇒ CA sẽ kiểm tra xác minh danh tính ⇒ Xác minh thành công sẽ cấp pre-certificate
2. CA gửi pre-certificate này tới nhiều CT log ⇒ Tạo ra một Signed Certificate Timestamp (SCT)
   1. Mỗi log được vận hành bởi 1 tổ chức khác nhau
   2. SCT là bằng chứng mật mã chứng minh chứng chỉ được gửi tới log tại một thời điểm cụ thể
   3. SCT được đưa vào chứng chỉ cuối cùng được cấp cho chủ sở hữu website
3. Khi Browser kết nối tới website ⇒ Kiểm tra SCT của chứng chỉ dựa trên CT log công khai xác nhận chứng chỉ được cấp và ghi log đúng cách ⇒ Nếu hợp lệ sẽ thiết lập kết nối an toàn, nếu không sẽ hiển thị cảnh báo



### Cấu trúc của CT logs

Sử dụng cấu trúc Merkle tree

{% code overflow="wrap" lineNumbers="true" expandable="true" %}
```
Để đảm bảo tính toàn vẹn và khả năng chống giả mạo của CT logs, chúng sử dụng một cấu trúc mật mã gọi là Merkle tree.

Cấu trúc này tổ chức các chứng chỉ theo dạng cây, trong đó mỗi nút lá (leaf node) đại diện cho một chứng chỉ, còn mỗi nút không phải lá (non-leaf node) đại diện cho giá trị hash của các nút con của nó.

Gốc của cây, được gọi là Merkle root, là một giá trị hash duy nhất đại diện cho toàn bộ log.

Hãy hình dung điều này thông qua một Merkle tree giả định dành cho inlanefreight.com:

Trong cây giả định này:

Root Hash: Nút nằm trên cùng, là một giá trị hash duy nhất đại diện cho trạng thái của toàn bộ log.
Hash 1 & Hash 2: Các nút trung gian, mỗi nút là giá trị hash của hai nút con — có thể là chứng chỉ hoặc các giá trị hash khác.
Cert 1 - Cert 4: Các nút lá đại diện cho từng chứng chỉ SSL/TLS riêng biệt dành cho các subdomain khác nhau của inlanefreight.com.

Cấu trúc này cho phép xác minh hiệu quả bất kỳ chứng chỉ nào trong log. Bằng cách cung cấp Merkle path — một chuỗi các giá trị hash — cho một chứng chỉ cụ thể, bất kỳ ai cũng có thể xác minh rằng chứng chỉ đó thực sự tồn tại trong log mà không cần tải xuống toàn bộ log.

Ví dụ, để xác minh Cert 2 (blog.inlanefreight.com), bạn sẽ cần:

Hash của Cert 2: Giá trị này trực tiếp xác minh chính chứng chỉ đó.
Hash 1: Xác minh rằng hash của Cert 2 được ghép đúng với hash của Cert 1.
Root Hash: Xác nhận rằng Hash 1 là một phần hợp lệ của cấu trúc log tổng thể.

Quá trình này đảm bảo rằng ngay cả khi chỉ một bit dữ liệu trong chứng chỉ hoặc trong chính log bị thay đổi, Root Hash cũng sẽ thay đổi, ngay lập tức báo hiệu rằng dữ liệu đã bị can thiệp.

Điều này khiến CT logs trở thành một công cụ vô cùng giá trị để duy trì tính toàn vẹn và độ tin cậy của các chứng chỉ SSL/TLS, qua đó tăng cường bảo mật Internet.
```
